核心问题清单
6 个已识别问题 · 按严重度排序
#1
无 API 抽象层 HIGH
路由函数直接写 SQL 查 SQLite，10+ 文件重复查询相同表。
pipeline_runs 在 4 个文件中用几乎相同的 SQL 查询。
前端完全耦合在数据库 schema 和文件路径上。
#2
两套运行记录表 HIGH
runs 表 (run_control.py) 和 pipeline_runs 表 (graph 节点) 各自独立。
"运行控制"页面和"运行列表"页面显示不同数据。
后台任务写入 runs，管线节点写入 pipeline_runs。
#3
混合数据源 MID
报告列表需合并 pipeline_runs + 文件系统 JSON + markdown 文件。
同一概念的报告，数据可能来自 3 个不同位置。
优先级逻辑复杂，难以推理。
#4
Storage 层不完整 MID
现有 Storage 类只覆盖 groups/members/core_topics。
其余（pipeline_runs, feedback, reports）全部裸 SQL。
扩展 Storage 是最直接的改进路径。
#5
后台任务绕过连接管理 MID
每个后台 task 自开 aiosqlite.connect()。
无连接池、无事务协调。
多群并行时可能 SQLITE_BUSY。
#6
模板引擎重复初始化 LOW
4 个模块仍自建 Jinja2 Environment，未用共享 _render.py。
辅助函数 (_format_ts, _status_chip) 在多个文件重复定义。
影响总结
后端改动 → 前端断裂
管线改了字段/路径，前端全部要手动追踪修改
无法独立演进
前端被锁死在 Jinja2 + HTMX，无法换框架

改造前后对比
BEFORE — 现状
❌ 路由函数内嵌 SQL（200-500 行/函数）
❌ 直接读取文件系统 JSON
❌ 两套 run 表，数据不一致
❌ 改管线 = 手动追踪修改所有页面
❌ 无法换前端框架
❌ 后台任务自开 DB 连接
AFTER — 目标
✓ 路由函数 < 30 行，只调 Service
✓ Repository 统一文件/DB 访问
✓ 合并为单一 run 数据源
✓ 改管线只改 Repository 映射
✓ Service 层同时支持 JSON + HTML
✓ 连接池统一管理
建议实施顺序
Phase 1 — 止血
· 合并 runs / pipeline_runs
· 统一 DB 连接管理
· 消除后台任务自开连接
Phase 2 — Repository 层
· 创建 Pydantic 数据模型
· 按 domain 拆分 Repository
· 替换所有内嵌 SQL
Phase 3 — Service 层
· 创建 Service 类封装业务逻辑
· 路由函数改调 Service
· 前端可自由选择 JSON API 或 HTML
