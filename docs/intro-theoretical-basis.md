# z-winnow 核心理论与思想基础

> 面向群成员介绍页（intro-landing）第 4 节「设计的理论基础」的信源。由用户提供，作为文案锚点。
> 产出方在写页面文案时以此为权威；如有更新，替换本文件。

## 一、问题：群聊知识无法被有效复用

微信群聊产生大量有价值的讨论，但这些知识以连续信息流的形式存在——一条消息出现、被看到、被淹没，事后检索需要精确的关键词或时间点。现有方案（翻聊天记录、关键词搜索、AI 摘要）各自解决了一个侧面，但共同的问题是：知识只存在一次，然后用完即丢。没有被沉淀、被校正、被跨日关联的可能。

项目的核心假设是：如果把群聊信息流视为高噪声源，把知识沉淀视为降噪压缩过程，那么设计一个多层管道来处理这个压缩过程，比用单一方法（如简单摘要）更有可能保留有效信息。这个假设在实践中表现为三层架构。

## 二、架构：三层信息处理

项目实际运行的管道将信息处理分为三个阶段，每个阶段解决一个独立问题：

L1（raw_messages）——全量保存。原始消息不可变写入，附带 serverID 可用于溯源。这一层的存在理由是：一旦丢弃就无法回溯，而压缩决策（哪些重要、哪些不重要）不应该在信息进入管道之前就做出。

L2（parsed_contexts）——单条消息增强。群聊不只有纯文本：图片需要 Vision 分析、卡片和链接需要结构化解析。这一层在不跨消息的前提下，把每条消息本身承载的信息提取完整。

L3（核心知识层）——跨消息压缩产出。议题摘要、资源列表、日报。这一层丢弃了大部分原始细节，只保留管道判定为"有价值"的内容。这是真正的压缩发生的地方。

三层不是从理论推导出来的架构，而是项目在运作中自然地分化的：每一层解决一个不同的问题，独立存储、独立版本、耦合度低。

## 三、L3 压缩质量与 Wan（2025）框架的对应

Wan 等人在发表于 The Innovation Informatics 的论文《Understanding as Compression: A New Framework for Evaluating LLMs》（2025）中提出，模型智能水平可以通过三个压缩层次来衡量：

1. 逐字记录的精确性（符号压缩）
2. 跨上下文的一致性（泛化压缩）
3. 提取核心语义、丢弃噪声的能力（语义压缩）

L1/L2/L3 的分层方式与这三个层次在形式上构成对应：L1 追求精确记录（符号层），L2 追求跨上下文理解（泛化层），L3 追求核心语义提取（语义层）。这个对应是设计层面的概念参照，不是定理意义上的映射——Wan 的框架是用来评估模型输出的，不是用来设计数据管道的。但参照本身是有用的：它把"为什么要分三层"从经验直觉提升到了一个可讨论的层面。

## 四、反馈回路：单向压缩的校正机制

管道是直线的（data_fetch → content_enrich → orchestrator → unified_reporter → output_composer），没有回流。这意味着压缩产出一旦写入就没有自动修正的途径。

这是所有单向处理系统的共性约束。反馈系统的设计目的是在这个直线管道外补一条侧路：群成员通过 submit_feedback 提交纠错或补充，下一周期运行时已接受的反馈通过 correction_loader 注入提示词影响压缩决策，版本化设计使每条反馈都可溯源可回滚。

核心设计假设：管道的单次压缩质量有限，人的参与可以持续校准。

## 五、验证方法

管道的压缩质量目前可以通过以下方式检验：

1. 人工对标——打开同天原始群聊与 L3 产出逐议题核对。最可靠但不可扩展。
2. 检索召回测试——通过 search_topics 搜索预期内容检查是否命中。可自动化但只测召回不测精度。
3. 反馈回路验证——对不满意的内容提交 correction 观察下周期是否改进。验证了可修正性但无法评估原始质量。
4. 压缩-解压-比对实验（待实施）——将 L3 知识改写为问答对，由无原始上下文的 LLM 回答，与原始消息比对语义差距。存在 LLM 不能充当自身质量评判者的裁判困境问题。
